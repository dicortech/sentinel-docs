Mantis Test Application

The Mantis Test Application is a comprehensive video processing and streaming application that combines advanced video pipeline management with RTSP streaming and real-time object tracking capabilities. It enables seamless switching between multiple video sources while providing simultaneous RTSP streaming and optional PID-based object tracking for camera control.

Features​

  • Dual Video Pipeline Management: Switch between two independent GStreamer video pipelines in real-time
  • RTSP Streaming Server: Stream video from multiple sources via RTSP protocol
  • Object Tracking Integration: PID-based object tracking with MQTT communication
  • Interactive Controls: Runtime control via keyboard commands
  • Flexible Pipeline Configuration: Support for custom GStreamer pipelines from files or command-line
  • Automatic Device Detection: Video device numbers are automatically extracted from pipeline files
  • Auto-Link Mode: Automatically synchronize PID tracking source with video source switching
  • Shared Memory Transport: Uses shared memory sockets for efficient inter-process communication

Architecture​

The application consists of three main components:

  1. MantisVideoSwitcher: Manages dual video pipelines with input-selector for seamless switching
  2. RTSPServer: Provides RTSP streaming capability for video distribution
  3. Object Tracking Integration: PID controller for camera pan/tilt based on object detection (optional)

Build Instructions​

Prerequisites​

Build Dependencies

Before building mantis_test_app, you must first build the PID Object Tracker library (pid_otrack). The application depends on libpid_otrack.so which needs to be compiled separately.

Build order:

  1. Build pid_otrack library (see PID Object Tracker documentation)
  2. Build mantis_test_app

For Yocto builds, the recipe handles this automatically. For standalone SDK builds, ensure the pid_otrack library is built in ../../sentinal_sdk/image/pid_otrack/build/ before running make.

Yocto SDK Toolchain Setup

For standalone SDK builds using the Yocto toolchain, you must first create and source the SDK environment before building. See the Toolchain Setup documentation for instructions on creating and installing the SDK toolchain.

# Source the SDK environment
source /path/to/sdk/environment-setup-<arch>-poky-linux

# Then proceed with building
cd apps/mantis_test_app
make

Required Dependencies:

  • GStreamer 1.0 development libraries
    • gstreamer-1.0
    • gstreamer-rtsp-server-1.0
  • PID Object Tracker library (pid_otrack) - Must be built first
  • libmosquitto (MQTT client library)
  • libcjson (JSON parsing)
  • C++11 compatible compiler
  • pthread support

Building​

cd apps/mantis_test_app
make

Build Configuration​

The Makefile supports the following variables:

Clean Build​

Installation​

Usage​

Before Running​

Required Setup

Before running the application, complete the following setup steps:

1. Create required directories:

mkdir -p /tmp/videos /tmp/images

These directories are used by:

  • dctvrecord plugin: Saves recorded video files to /tmp/videos/
  • dctfcapture plugin: Saves captured frame images to /tmp/images/

2. Configure MQTT Broker IP in Pipeline Files:

The example pipeline files contain a default MQTT broker IP (169.254.1.222) in the dctotrack and dctoverlay GStreamer elements. You must update this to match your board's actual IP address for MQTT communication to work properly.

# On target device - update all pipeline files
sed -i 's/mqtt-broker=169.254.1.222/mqtt-broker=192.168.1.100/g' \
    /usr/share/sentinel-sdk/mantis_test_app/*.txt

# During development - update pipeline files
sed -i 's/mqtt-broker=169.254.1.222/mqtt-broker=192.168.1.100/g' \
    example_pipelines/*.txt

Or manually edit the pipeline files and change:

mqtt-broker=169.254.1.222

to your board's IP address, for example:

mqtt-broker=192.168.1.100
info

The --mqtt-broker command-line option only configures the PID tracker module's MQTT client, not the GStreamer pipeline's MQTT settings. You must edit the pipeline files to change the MQTT broker IP used by dctotrack and dctoverlay plugins.

Basic Usage​

./mantis_test_app --file <pipeline1_file> <pipeline2_file>

Or with direct pipeline strings:

./mantis_test_app "<pipeline1_string>" "<pipeline2_string>"

Pipeline Configuration​

What are Pipeline Files?​

Pipeline files are text files containing GStreamer pipeline definitions. Each file describes a complete video processing pipeline from source to output, including optional AI features like object detection, tracking, video recording, and frame capture.

The application loads two pipeline files at startup - one for each video source that can be switched between during runtime.

Pipeline File Format​

Pipeline files use standard GStreamer pipeline syntax with the following requirements:

Required Components:

  1. Video Source: Typically v4l2src device=/dev/videoN (the application auto-detects N)
  2. Shared Memory Output: Must end with shmsink socket-path=/tmp/videoN.socket (N must match device number)
  3. H.264 Encoding: Required for RTSP streaming with format video/x-h264,stream-format=byte-stream,alignment=au
  4. Proper Queuing: Use queue elements for smooth playback
important

The device number N must be consistent across device=/dev/videoN, socket-path=/tmp/videoN.socket, and mqtt-topic="tracking/videoN" within each pipeline file. The application automatically extracts this number to configure RTSP streaming.

Optional Components:

  • Object Detection: dctobd or obd elements
  • Object Tracking: dctotrack element (publishes to MQTT)
  • Visual Overlay: dctoverlay element (subscribes from MQTT)
  • Video Recording: dctvrecord element (triggered by detections)
  • Frame Capture: dctfcapture element (periodic or triggered)
  • Tee Elements: For branching pipeline to multiple outputs

Basic Pipeline Structure​

v4l2src device=/dev/videoN
  ↓
[videoconvert + videoscale]
  ↓
[tee: split to detection path and display path]
  ↓                          ↓
[obd/dctobd]              [dctoverlay]
  ↓                          ↓
[dctotrack → MQTT]        [videoconvert]
                             ↓
                          [h264 encode]
                             ↓
                          [tee: split to recording and streaming]
                             ↓                    ↓
                       [dctvrecord]          [shmsink]
                             ↓
                       [dctfcapture]

Pipeline File Location​

Example pipelines are located at different paths depending on your environment:

On Target Device (Yocto Image):

/usr/share/sentinel-sdk/mantis_test_app/

Development Environment (Source Tree):

apps/mantis_test_app/example_pipelines/
tip

When running on the target device, use the absolute path /usr/share/sentinel-sdk/mantis_test_app/ to access the pre-installed pipeline files. During development with the SDK, use the relative path example_pipelines/ from the application directory.

How to Use Pipeline Files​

Method 1: Using --file flag (Recommended)

On target device:

mantis_test_app --file /usr/share/sentinel-sdk/mantis_test_app/pipeline_video4_rtsp_vrec.txt \
                      /usr/share/sentinel-sdk/mantis_test_app/pipeline_video8_rtsp_vrec.txt

During development:

./mantis_test_app --file example_pipelines/pipeline_video4_rtsp_vrec.txt \
                        example_pipelines/pipeline_video8_rtsp_vrec.txt

Method 2: Direct pipeline strings

./mantis_test_app "v4l2src device=/dev/video4 ! ... ! shmsink socket-path=/tmp/video4.socket" \
                  "v4l2src device=/dev/video8 ! ... ! shmsink socket-path=/tmp/video8.socket"
note

Using pipeline files is recommended as they're easier to maintain and modify.

Creating Custom Pipelines​

To create a custom pipeline file:

  1. Copy an existing pipeline as a template:

    On target device:

    cp /usr/share/sentinel-sdk/mantis_test_app/pipeline_video4_rtsp_vrec.txt my_custom_pipeline.txt

    During development:

    cp example_pipelines/pipeline_video4_rtsp_vrec.txt my_custom_pipeline.txt

  2. Modify key parameters (ensure device number N is consistent):

    • Video device: Change device=/dev/videoN
    • Socket path: Update socket-path=/tmp/videoN.socket (N must match device number)
    • MQTT topic: Change mqtt-topic="tracking/videoN" (N should match device number)
    • Resolution: Modify width= and height= values
    • MQTT broker: Update mqtt-broker= and mqtt-port=
    • Detection classes: Modify enabled-classes="bottle,person,car"
    • Recording location: Change location=/tmp/videos
    warning

    The device number must be consistent throughout the pipeline (e.g., if using /dev/video4, use /tmp/video4.socket and tracking/video4)

  3. Test the pipeline:

    gst-launch-1.0 $(cat my_custom_pipeline.txt)

  4. Use in application:

    ./mantis_test_app --file my_custom_pipeline.txt <pipeline2.txt>

RTSP Streaming​

RTSP streams are automatically created based on the video device numbers detected from your pipeline files. The device numbers are extracted from the device=/dev/videoN parameter in your pipeline configuration.

For example, if your pipelines use:

  • Pipeline 1: device=/dev/video4 → Stream available at rtsp://<ip-address>:6000/video4
  • Pipeline 2: device=/dev/video8 → Stream available at rtsp://<ip-address>:6000/video8

Accessing RTSP Streams​

Using VLC Player:

vlc rtsp://192.168.1.100:6000/video4
vlc rtsp://192.168.1.100:6000/video8

Using GStreamer:

gst-launch-1.0 rtspsrc location=rtsp://192.168.1.100:6000/video4 ! \
    rtpjitterbuffer ! rtph264depay ! h264parse ! avdec_h264 ! \
    videoconvert ! autovideosink sync=false
note

The video device numbers (4, 8, etc.) are automatically detected from your pipeline files. You can use any video device number your system supports, and the RTSP URLs will adjust accordingly.

Object Tracking Workflow​

  1. Start application with --enable-tracking
  2. Press S to view available object IDs
  3. Press I to set target ID to track
  4. Press T to enable tracking
  5. Press P to manually switch PID input source
  6. Press A to enable auto-link (PID follows video switching)

Status Information​

Press S to display:

  • Current video source (1 or 2)
  • Current PID source and MQTT topic
  • Auto-link mode status (ON/OFF)
  • Tracking enabled/disabled
  • MQTT connection status
  • Current target ID
  • List of available object IDs

Troubleshooting​

Pipeline Fails to Start​

  • Check that video devices exist: ls /dev/video*
  • Verify GStreamer elements are installed: gst-inspect-1.0 <element>
  • Check pipeline syntax in configuration files
  • Ensure custom GStreamer plugins (dctobd, dctotrack, etc.) are installed

RTSP Stream Not Available​

  • Verify shared memory sockets exist: ls /tmp/video*.socket
  • Check firewall allows port 6000
  • Ensure pipelines are outputting to correct socket paths
  • Check GStreamer pipeline is running without errors

Object Tracking Not Working​

  • Verify MQTT broker is accessible: mosquitto_sub -h <broker> -t "#"
  • Check MQTT topics in pipeline configuration match tracking config
  • Verify PID object tracker library is built and installed
  • Press S to check MQTT connection status
  • Enable debug logging: GST_DEBUG=3 ./mantis_test_app ...

Cleanup Issues on Exit​

  • First Ctrl+C initiates graceful shutdown (waits for EOS)
  • Second Ctrl+C forces immediate exit
  • Third Ctrl+C performs emergency termination
  • Socket files are automatically cleaned up on proper exit

Performance Issues​

  • Reduce frame rate in pipeline configuration
  • Increase detection frameinterval to process fewer frames
  • Lower video resolution
  • Disable recording or frame capture features if not needed

API Integration​

PID Object Tracker API​

The application integrates with the PID object tracker library (lib-pid-otrack.h):

// Initialize tracker
DctotrackPID::MQTTObjectTracker tracker(model_res, display_res);
tracker.getTracker()->initializeWithConfig("mantis_app");
tracker.getTracker()->ai_obj_trk_enable();

// Calculate pan/tilt commands
auto command = tracker.getTracker()->calculatePanTiltCommand();
if (command.valid) {
    // Use command.pan_delta and command.tilt_delta for camera control
}

For full API documentation, see PID Object Tracker.

Signal Handling​

The application handles signals gracefully:

  • SIGINT/SIGTERM: Initiates graceful shutdown with EOS propagation
  • Multiple signals: Progressively forces faster shutdown
  • Emergency exit: Three consecutive signals perform immediate termination

Performance Notes​

  • Shared memory transport minimizes CPU overhead
  • RTSP streaming uses minimal buffering for low latency
  • PID tracking runs at ~10Hz in separate thread
  • Video switching is seamless without frame drops
